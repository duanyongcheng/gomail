## 2026-11-05：Gmail 403 限流修复与复验

### 已确认的根因和改动

## 2026-11-20：长回填路径的健壮性修复（未复现 400）

本轮只做代码层加固和合成验证，**没有连接真实 Gmail**，不改变上表任何一行的状态。基线 `df47229` 加本批修改。

### 修复的三个缺陷

1. **401 刷新在退避后失效**：403 修复把 `for attempt := 0; attempt < 3` 改成了无限循环，但刷新条件仍写作 `attempt == 0`。一次读取若先经历限流退避，后来的 access token 过期得到 401 时永远不会触发刷新。改为按 `authRetries` 计数，一次请求最多刷新一次，并补回归用例。
2. **截断的 2xx 响应被当成坏邮件**：原始邮件 GET 超过 4–68 MiB 且走 gzip 时，`net/http` 的透明解压有可能在 `ReadAll` 无错的情况下提前结束；此前的 `json.Unmarshal` 失败被统一映射成 `ContentError{invalid_content}`，于是这封邮件被静默放进下载失败队列、扫描继续前进。现在只有「以 `{` 开头、却不是合法 JSON」的 2xx 响应才判定为截断，并作为传输型错误返回——回填在已提交前缀处停下并保留断点，下次照常续传；中介返回的 HTML/散文仍按坏内容处理。
3. **访问状态变化被当成坏邮件**：`pageBatch.fetch` 只识别 404 和 `ContentError`，其它错误（含 `AccessError`）直接终止整个 pass，原先无法区分「账户被阻断」和「这封邮件坏了」。现在先解析一次错误原因，`AccessError` 明确按 pass 失败处理，不会写入下载失败队列。

同时新增 `fetchOnce`：单封邮件的解码/体积/MIME 解析失败在页内最多尝试 3 次，其余远程与传输错误不在此重试——有界读取重试仍只属于 `googleapi`。
